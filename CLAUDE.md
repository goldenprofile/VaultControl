# CLAUDE.md

Инструкции для AI-агентов, работающих с репозиторием **vaultctl**.

## Что это за проект

**vaultctl** — самостоятельный исполнительный слой (execution layer / agentic runner): принимает задачи извне и разворачивает CLI-агента  с этими задачами и путём к vault. Сам vaultctl не читает и не пишет в vault и не содержит логики навыка — операции над файлами выполняет запущенный CLI-агент через навык `obsidian`.

Ключевые роли:

| Компонент            | Роль                                                        | Где живёт                  |
|----------------------|--------------------------------------------------------------|----------------------------|
| **vaultctl**         | Execution layer / agentic runner — точка входа, мост между вызывающей стороной и CLI-агентом | Этот репозиторий           |
| **Skill `obsidian`** | Переиспользуемый навык (плагин), выполняется внутри CLI-агента | Отдельный пакет / skill    |
| **Obsidian Vault**   | Целевое хранилище Markdown                                    | Файловая система пользователя |

vaultctl **не содержит** сам навык внутри себя как основную поставку. Навык подключается извне (как skill/plugin для Claude Code, Codex, Grok и других CLI-агентов, поддерживающих Agent Skills) и активируется тем CLI-агентом, которого запускает vaultctl.

## Принципы

1. **Разделение ответственности**  
   - vaultctl отвечает за приём задач, резолв пути к vault и запуск CLI-агента (subprocess) — сам не трогает файлы vault.  
   - Skill `obsidian` отвечает за конкретные операции с файлами vault (клиппинг, задачи, ADR, ревью и т.д.) и выполняется внутри запущенного CLI-агента.

2. **Filesystem-first**  
   Все операции с vault идут через файловую систему (Read / Write / Edit / Glob / Grep / Bash). Не требуется запущенный Obsidian.

3. **Навык — внешняя зависимость**  
   Не копируй содержимое навыка `obsidian` в этот репозиторий без явной необходимости. Держи ссылку/инструкцию по установке навыка.

4. **Язык**  
   Документация и пользовательские сообщения — на русском. Технические идентификаторы и поля frontmatter — на английском.

## Чего не делать

- Не дублировать детальную логику workflow навыка (клиппинг, задачи, ADR и т.д.) внутри vaultctl — это ответственность skill `obsidian`.
- Не хардкодить абсолютные пути vault.
- Не требовать запущенный Obsidian или конкретные плагины Obsidian для базовой работы.
- Не смешивать роли: vaultctl ≠ skill.

## Ловушки запуска агента

По умолчанию задача добавляется **последним аргументом** команды агента (`runner.build_command`). Следствия, проверенные на живых прогонах:

- Флаг, забирающий список значений (у Claude Code — `--allowedTools`), не должен стоять в конце `--agent-cmd`: он проглотит текст задачи, и агент ответит `Input must be provided`. Держи `-p` последним.
- Команда разбирается через `shlex` в posix-режиме, поэтому путь с обратными слэшами обязателен в кавычках — иначе слэши съедаются.
- Для клиппинга URL агенту нужен `WebFetch`. Без него навык сохраняет заглушку вместо содержимого страницы — операция формально успешна, а результат пустой.

## Ловушки передачи текста

Аргумент командной строки — плохой канал для длинного текста, и ломается он **до** запуска vaultctl:

- **Многострочная вставка в PowerShell подвешивает ввод.** `vlt "` плюс вставка из буфера — PSReadLine видит незакрытую строку и ждёт продолжения (`>>`). Выглядит как зависание vlt, хотя процесс ещё не стартовал.
- **PowerShell раскрывает `$` в двойных кавычках.** `В API стоит $0,15/$0,5` доезжает до агента как `В API стоит ,15/,5` — цены пропадают молча.
- **Windows обрывает командную строку на 32767 символах.** Пост влезает, статья целиком — уже нет.

Поэтому текст подаётся мимо argv: `--clipboard`, `--file`, пайп или интерактивный ввод (`vaultctl/taskinput.py`), а argv остаётся под короткую инструкцию («clip:», «NameRegister:»). Дальше `resolve_agent_input` решает, уйдёт задача аргументом или в stdin агента.

- В stdin задача пишется **байтами в UTF-8**. Текстовый режим `subprocess` на Windows заменил бы `\n` на `\r\n`, и агент получил бы не тот текст.
- Буфер обмена на Windows читается через `Get-Clipboard` с форсированным `[Console]::OutputEncoding=UTF8`: Windows PowerShell 5.1 при перенаправлении отдаёт cp866.

- **Хвост вставки живёт в очереди ввода консоли.** Строки после первой шелл выполняет как команды, когда освободится, — уже после завершения агента. `console.flush_input` сбрасывает очередь до запуска агента и после него (`--keep-input` отключает); на пайп и перенаправленный файл это не распространяется. В ctypes-обёртке обязательны `argtypes`/`restype`: без них 64-битный `HANDLE` усекается до int и сброс тихо не срабатывает.

`claude -p` молчит от старта до финального ответа, поэтому долгая задача тоже выглядит зависшей. Флаг `--stream` добавляет агенту `--output-format stream-json --verbose` и печатает шаги по мере работы; формат разбирается только для Claude Code (`progress.supports_stream`).

## Окружение и команды

Проект использует **uv**. Версия Python закреплена в `.python-version`, зависимости — в `pyproject.toml`, точные версии — в `uv.lock` (коммитится).

| Задача                    | Команда                      |
|---------------------------|------------------------------|
| Поставить окружение       | `uv sync`                    |
| Запустить тесты           | `uv run pytest`              |
| Запустить CLI (локально)  | `uv run vaultctl "<задача>"` (алиас: `vlt`) |
| Установить глобально     | `uv tool install --editable .` (см. [docs/global-install.md](docs/global-install.md)) |
| Добавить зависимость      | `uv add <пакет>`             |
| Добавить dev-зависимость  | `uv add --dev <пакет>`       |

Не используй `pip install` и не правь `uv.lock` вручную.

Локальные пути и секреты — в `.env` (в git не попадает), шаблон — `.env.example`. vaultctl подгружает его сам через python-dotenv, ища от текущей директории вверх по дереву; уже заданные переменные окружения приоритетнее и не перезаписываются.

## Как работать с навыком

При разработке/тестировании vaultctl предполагается, что навык `obsidian` уже установлен в окружении CLI-агента, которого запускает vaultctl (`--agent-cmd` / `VAULTCTL_AGENT_CMD`).

Если нужно проверить поведение навыка:

1. Убедись, что skill доступен выбранному CLI-агенту.
2. Дай vaultctl задачу, которая должна активировать навык (например: «сохрани ссылку», «добавь задачу в проект X»).
3. Проверь, что запущенный CLI-агент подхватил навык и результат появился в vault.
