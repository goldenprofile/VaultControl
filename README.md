# vaultctl

**vaultctl** — исполнительный слой (execution layer / agentic runner) для задач над хранилищем Obsidian. Мост между вызывающей стороной и CLI-агентом (Claude Code, Codex, Grok — любым агентом с поддержкой [Agent Skills](https://agentskills.io/specification)).

vaultctl принимает текст задачи, определяет путь к vault и запускает CLI-агента с этой задачей. Сам он **не читает и не пишет** в vault — все операции над файлами выполняет запущенный агент через навык `obsidian`.

## Архитектура

```
┌─────────────────────────────────────┐
│              vaultctl               │  ← этот проект (execution layer / agentic runner)
│  • принимает задачу                 │
│  • резолвит путь к vault            │
│  • запускает CLI-агента с задачей   │
└─────────────────┬───────────────────┘
                  │ запускает (subprocess)
                  ▼
┌─────────────────────────────────────┐
│  CLI-агент (Claude Code/Codex/Grok) │  ← подхватывает навык obsidian
│  • читает SKILL.md навыка           │
│  • выполняет операцию сам —         │
│    Read/Write/Edit/Glob/Grep        │
└─────────────────┬───────────────────┘
                  │
                  ▼
┌─────────────────────────────────────┐
│         Obsidian Vault              │
│  inbox/  projects/  logs/  maps/    │
└─────────────────────────────────────┘
```

- **vaultctl** — точка входа и запуск агента; логики работы с заметками не содержит.
- **obsidian skill** — переиспользуемый навык (инструкции + шаблоны), ставится в CLI-агента отдельно.
- Навык работает **filesystem-first**: агент читает и пишет Markdown напрямую, запущенный Obsidian не нужен.

Почему устроено именно так — [docs/adr/](docs/adr/).

## Текущее состояние

MVP-каркас: CLI работает end-to-end, интеграции и маршрутизация задач впереди.

Есть: приём задачи (аргумент, буфер обмена, файл, пайп, интерактивный ввод), резолв vault,
запуск агента подпроцессом с доставкой задачи аргументом или в stdin, статус запуска и
потоковый показ шагов, таймаут, различимые коды возврата. Подробности — в разделах ниже.

Пока нет:

- HTTP API, вебхуков и других способов приёма задач кроме CLI;
- маршрутизации задач и собственных системных промптов — задача уходит агенту как есть;
- разбора потока событий у агентов кроме Claude Code и pi — их вывод идёт как есть.

## Установка

Проект использует [uv](https://docs.astral.sh/uv/). Версия Python закреплена в `.python-version` (3.13), нижняя граница совместимости — 3.10.

```bash
uv sync
```

Команда создаст `.venv`, поставит зависимости из `uv.lock` и установит `vaultctl` в editable-режиме. Дальше — либо `uv run vaultctl ...`, либо активированное окружение.

Скопируйте `.env.example` в `.env` и укажите путь к своему vault:

```bash
cp .env.example .env
```

В шаблоне уже лежит рабочая команда запуска Claude Code с набором инструментов, которого хватает навыку `obsidian`, — включая `WebFetch`, без которого клиппинг URL сохранит заглушку вместо содержимого страницы.

Чтобы `vlt` и `vaultctl` работали из любой папки — `uv tool install --editable .`.
Настройка переменных окружения вне проекта и разбор проблем:
[Глобальная установка vlt](docs/global-install.md).

## Использование

```bash
uv run vaultctl "сохрани ссылку https://example.com/post"
uv run vlt "сохрани ссылку https://example.com/post"   # vlt — тот же самый вход
uv run vlt Сделай бриф по проекту NameRegister         # кавычки необязательны
```

Позиционные аргументы склеиваются в одну задачу.

### Длинный текст: не через аргумент

Скопированный пост или статью **нельзя передавать аргументом** — сломается до
того, как vaultctl запустится:

- вставка нескольких строк после открывающей кавычки подвешивает ввод в
  PowerShell: шелл ждёт закрывающую кавычку (`>>`), а выглядит это как зависший
  `vlt`;
- в двойных кавычках PowerShell раскрывает `$`: `стоит $0,15/$0,5` доезжает
  до агента как `стоит ,15/,5`;
- Windows обрывает командную строку на 32767 символах.

Поэтому текст подаётся отдельно, а в аргументе остаётся короткая инструкция:

```bash
# из буфера обмена — основной сценарий «скопировал пост, сохрани в vault»
vlt -c "clip: сохрани этот пост"

# пайпом
Get-Clipboard -Raw | vlt "clip:"
cat post.txt | vlt "clip:"

# из файла
vlt --file post.txt "clip:"

# интерактивно: без аргументов vlt сам попросит текст
# (конец ввода — Ctrl+Z и Enter на Windows, Ctrl+D на Linux/macOS)
vlt
```

Инструкция из аргументов становится первой строкой задачи, текст — блоком под
ней. Источник текста ровно один: `--clipboard`, `--file` и `--stdin`
взаимоисключающие.

**При `-c` вставлять в терминал вообще ничего не нужно** — текст уже в буфере,
vaultctl заберёт его сам. Достаточно `vlt -c`.

### Хвост вставки и очередь ввода терминала

Если многострочный текст всё же попал в терминал, PowerShell берёт первой
строкой команду, а остальные строки остаются в очереди ввода консоли и
выполняются как отдельные команды — когда предыдущая команда завершится. После
долгого запуска агента это выглядит как шквал ошибок из текста заметки:

```
❯ - GLM 5.3 Flash (https://t.me/ai_newz/4726) — Бывшая Ox Alpha ...
ParserError: Missing expression after unary operator '-'.
```

vaultctl сбрасывает очередь ввода терминала — до запуска агента и после его
завершения, — чтобы этот хвост не ушёл в шелл командами. Если вы намеренно
набираете следующую команду, пока агент работает, отключите сброс флагом
`--keep-input`. На пайп и перенаправленный файл это не распространяется: там
ввод — данные, а не хвост вставки.

### Что происходит, пока агент работает

Перед запуском vaultctl печатает в stderr, что именно он делает, — молчание
`pi -p` до финального ответа иначе неотличимо от зависания:

```
▶ vault: D:\Work\Obsidian-Vaults\alpha-llc
▶ агент: claude --allowedTools WebFetch,Read,Write,Edit,Glob,Grep -p
▶ задача: 4412 символов, 41 строк (аргумент)
```

Флаг `--stream` (или `VAULTCTL_STREAM=1`) показывает и сами шаги агента:

```
▶ агент запущен (claude-opus-5)
  · Skill(obsidian)
  · WebFetch(https://t.me/ai_newz/4726)
  · Write(inbox/2026-09-02-neurodigest.md)
✔ готово за 47 с, $0.12
```

Для этого vaultctl добавляет агенту флаги потока: Claude Code — `--output-format stream-json --verbose`, pi — `--mode json`. Формат разбирается у этих двух; для другого агента vaultctl предупредит и оставит вывод как есть. Строки статуса убираются флагом `--quiet`.

### Переменные окружения

Перед работой vaultctl подгружает `.env`: без `--env-file` файл ищется от текущей рабочей директории вверх по дереву. Переменные, уже заданные в окружении, приоритетнее — `.env` их не перезаписывает.

| Переменная             | Назначение                                        |
|------------------------|---------------------------------------------------|
| `OBSIDIAN_VAULT_PATH`  | путь к vault                                      |
| `VAULTCTL_AGENT_CMD`   | команда запуска CLI-агента                        |
| `VAULTCTL_TIMEOUT`     | ограничение на работу агента, сек (по умолчанию нет) |
| `VAULTCTL_AGENT_INPUT` | канал доставки задачи агенту: `auto`, `arg`, `stdin` |
| `VAULTCTL_STREAM`      | `1` — показывать шаги агента по ходу работы        |

На Windows путь в `.env` пишите без кавычек или в одинарных: в двойных dotenv раскроет escape-последовательности, и путь вроде `D:\Work\alpha` сломается на `\a`.

### Определение vault

Порядок резолва:

1. переменная окружения `OBSIDIAN_VAULT_PATH` — из шелла или из `.env` (должна указывать на существующую директорию);
2. иначе — ближайшая родительская директория текущей рабочей, содержащая папку `.obsidian/`.

Если ни то, ни другое не сработало — vaultctl завершается с ошибкой и кодом `1`.

### Выбор CLI-агента

Команду берём из `--agent-cmd "codex exec"`, иначе из `VAULTCTL_AGENT_CMD`, иначе
встроенное умолчание `pi -p`.

Команда разбирается через `shlex`, текст задачи по умолчанию добавляется последним аргументом. Отсюда два правила, которые легко нарушить:

**Флаг со списком значений не должен стоять последним.** Он проглотит задачу:

```bash
# ✗ агент ответит «Input must be provided» — --allowedTools забрал текст задачи
--agent-cmd "pi -p --allowedTools WebFetch,Read,Write"

# ✓ -p последний, задача уходит агенту
--agent-cmd "claude --allowedTools WebFetch,Read,Write -p"
```

**Путь с обратными слэшами берите в кавычки** — иначе `shlex` их съест и `C:\bin\claude.exe` превратится в `C:binclaude.exe`:

```bash
--agent-cmd '"C:\Users\me\.local\bin\claude.exe" -p'
```

**npm-шимы `.cmd` vaultctl разворачивает сам.** На Windows агенты из npm (pi) — это `.cmd`-шимы, которые subprocess запустить не может («pi есть в PATH, но vaultctl его не находит»). vaultctl сам вытаскивает из шимы путь к js-файлу и запускает агента через node — ничего прописывать не нужно (подробнее — [ADR-0004](docs/adr/0004-launch-npm-cmd-shims-through-node.md)). Если шима не разобралась, vaultctl подскажет задать `VAULTCTL_AGENT_CMD` в виде `"node <js-файл агента>"`.

Для клиппинга URL агенту нужен `WebFetch`: без него страница не скачается и в vault ляжет заглушка вместо разбора. Готовая команда — в `.env.example`.

### Канал доставки задачи агенту

`--agent-input` (или `VAULTCTL_AGENT_INPUT`) выбирает, как задача попадёт к агенту:

| Значение | Поведение                                                             |
|----------|------------------------------------------------------------------------|
| `auto`   | по умолчанию: аргументом, пока командная строка помещается в лимит ОС; длинный текст уходит в stdin |
| `arg`    | всегда последним аргументом                                            |
| `stdin`  | всегда потоком — агент должен уметь читать задачу из stdin (`pi -p` умеет) |

В stdin задача пишется байтами в UTF-8: в текстовом режиме Python на Windows
заменил бы `\n` на `\r\n`, и агент получил бы не тот текст.

### Опции

| Опция            | Описание                                                      |
|------------------|---------------------------------------------------------------|
| `-c/--clipboard` | взять текст задачи из буфера обмена                            |
| `-f/--file`      | взять текст задачи из файла                                    |
| `--stdin`        | взять текст задачи из stdin (при пайпе включается сам)         |
| `--agent-cmd`    | команда запуска CLI-агента                                     |
| `--agent-input`  | канал доставки задачи агенту: `auto`, `arg`, `stdin`           |
| `--env-file`     | путь к конкретному `.env` вместо поиска вверх по дереву        |
| `--timeout`      | ограничение на работу агента в секундах                        |
| `--stream`       | показывать шаги агента по мере работы (Claude Code)            |
| `-q/--quiet`     | не печатать строки статуса перед запуском                      |
| `--keep-input`   | не сбрасывать очередь ввода терминала                          |

### Коды возврата

| Код         | Значение                                                        |
|-------------|-----------------------------------------------------------------|
| `0`         | агент отработал успешно                                          |
| `1`         | не определён vault, нет указанного `--env-file`, кривой таймаут  |
| `124`       | агент не уложился в `--timeout` и был остановлен                 |
| `127`       | команда агента не найдена                                        |
| прочие      | код возврата запущенного CLI-агента                              |

## Навык `obsidian`

Распространяется отдельно (репозиторий `llm-skills`), актуальная версия — **1.2.0**. Ставится как skill/plugin в CLI-агента; vaultctl лишь разворачивает этого агента под конкретную задачу.

Что умеет навык: клиппинги (URL, статьи, сниппеты), проектные задачи, синтез исследований, ADR и решения, дневник работы, брифы проектов, периодические ревью, анализ структуры vault и графа тегов/ссылок.

Что нужно с его стороны: навык установлен в том CLI-агенте, которого запускает vaultctl,
и у агента есть доступ к файловой системе vault на чтение и запись.

Примеры задач, которые можно передать через vaultctl:

```
Сохрани эту статью: https://example.com/post
NameRegister: Добавить фильтр по цене в каталог
Сделай бриф по проекту NameRegister
Запиши решение: выбрали Tailwind, потому что...
Лог дня
```

## Разработка

```bash
uv sync            # окружение и зависимости
uv run pytest      # тесты
uv add <пакет>     # новая зависимость (обновит pyproject.toml и uv.lock)
```

`uv.lock` коммитится — окружение воспроизводится по нему один в один.

### Структура репозитория

```
vaultctl/
├── README.md               # этот файл
├── CLAUDE.md               # правила проекта для агентов (AGENTS.md — указатель на него)
├── pyproject.toml          # пакет, точка входа CLI, зависимости
├── uv.lock                 # зафиксированные версии зависимостей
├── .env.example            # шаблон переменных окружения
├── docs/
│   ├── adr/                # решения по архитектуре: контекст, альтернативы, последствия
│   └── global-install.md   # установка vlt как глобальной команды
├── vaultctl/
│   ├── cli.py              # разбор аргументов, точка входа `vaultctl`
│   ├── config.py           # загрузка .env, путь к vault, таймаут
│   ├── console.py          # сброс очереди ввода терминала
│   ├── taskinput.py        # сбор задачи: аргументы, буфер, файл, stdin, ввод
│   ├── progress.py         # строки статуса и разбор потока событий агента
│   └── runner.py           # сборка команды и запуск CLI-агента
└── tests/                  # по файлу на модуль + conftest с изоляцией os.environ
```
