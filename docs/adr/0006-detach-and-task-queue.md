# 0006. Очередь задач и detach — файловое состояние, отсоединённые воркеры, без демона

- **Статус:** Accepted
- **Дата:** 2026-09-04

## Контекст

vlt занимает терминал на весь прогон: типовая задача на pi — минуты, и параллельно
вторую не отдать. Нужны: detach (отдать задачу, вернуть терминал), очередь
(задачи, отданные во время работы другой, не теряются), наблюдение (список, лог
шагов, финальный ответ) и отмена. Решение обсуждалось в двух вариантах.

## Решение

Файловое состояние без демона. Каталог состояния `~/.local/state/vaultctl/`
(на всех платформах; в vault — нельзя: это пользовательские данные для
синхронизации):

- `runs/<id>.json` — задача: текст, vault (снимок на момент подачи), статус
  `queued → running → done | failed | cancelled`, pid, путь к логу, код
  возврата, финальный ответ агента;
- `logs/<id>.log` — статус-строки и поток событий агента (рендер StreamRenderer);
- `locks/worker.lock` — один воркер на систему; `locks/vault-<hash>.lock` —
  один агент на vault.

`vlt -d 'задача'` создаёт элемент `queued` и, если живого воркера нет,
запускает отсоединённую копию `python -m vaultctl.worker` (Windows:
`DETACHED_PROCESS | CREATE_NEW_PROCESS_GROUP`, POSIX: `start_new_session`;
stdin → NUL, вывод → `logs/worker.log`). Воркер берёт `worker.lock` (занят —
тихо выходит: гонка одновременных `-d` безопасна), разбирает очередь по одной
задаче и завершается, когда пусто: **поллинга и демона нет — воркеры релеят
очередь сами**.

Локи с pid-владельцем: `O_EXCL`-создание, занятый лок с мёртвым pid считается
устаревшим и перехватывается. `vault-<hash>.lock` берёт и блокирующий запуск:
второй vlt на тот же vault получает ошибку (код 3) с подсказкой `vlt -d` —
два агента, пишущих в один vault, ломают файлы друг друга. Воркер перед задачей
ждёт этот лок (отмену проверяет в ожидании).

Наблюдение: `vlt q` (список, сворачивая `running` с мёртвым pid в `failed`),
`vlt q log <id> [-f]`, `vlt q result <id>`, `vlt q cancel <id>` (queued —
отметить; running — убить дерево процессов, `taskkill /T`), `vlt q prune`.
Финальный ответ агента StreamRenderer отдаёт как `final_text`, воркер кладёт в
элемент очереди.

## Альтернативы

- **Демон `vlt serve`** — отверг: личный однопользовательский инструмент, а
  демону нужны автостарт, проверка живости, версионирование протокола CLI↔демон.
  Файловое состояние даёт те же гарантии при цене ~вдвое-втрое ниже и полностью
  наблюдаемо глазами.
- **Параллельные агенты** — отверг: они пишут в один vault и ломают файлы друг
  другу; очередь строго последовательная.
- **Состояние в vault** — отверг: vault синхронизируется и виден в Obsidian,
  служебные файлы там чужие.
- **Тосты-уведомления** — отложено (nice to have): `vlt q` закрывает наблюдение.

## Последствия

- (+) Терминал свободен сразу; очередь переживает завершение воркера и падения
  (reconcile чинит `running` с мёртвым pid), задачи привязаны к vault на момент
  подачи.
- (+) Блокирующий запуск защищён локом от повторного запуска поверх работающего.
- (−) Перезагрузка машины не возобновляет очередь сама: `queued` останутся
  файлами до следующего `-d` (который поднимет воркер) — для личного раннера
  приемлемо.
- (−) Отмена running-задачи убивает воркер целиком (дерево процессов): остаток
  очереди поднимается новым воркером, но текущая задача теряется без
  перезапуска — это и есть семантика отмены.
- (−) pid-локи подвержены переиспользованию pid; для персонального раннера риск
  принят, локи чинятся повторной подачей.
- Следствие: `StreamRenderer.final_text` — публичный способ достать финальный
  ответ из потока; `run_task(result_out=…)` — канал для воркера.
